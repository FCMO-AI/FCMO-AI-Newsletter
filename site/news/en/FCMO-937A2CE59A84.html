Anthropic adds server-side message threads to its Claude API

Anthropic’s Nov 2, 2026 platform release notes introduced beta message threads for the Claude Messages API and listed availability across Anthropic’s API and three managed cloud platforms. The official documentation says clients create a thread with the full conversation and continue it by sending only new messages plus the prior response ID; the service retains the conversation temporarily. Threads expire after five minutes without a request and are deleted within one hour after last use. Anthropic says this reduces repeated upload, validation and tokenization work, but reports no measured latency or cost results. The feature is not ZDR- or HIPAA-eligible and does not support compaction, context editing, token counting or message batches.

  • Claimed — Anthropic documents a create/continue interface that stores a conversation server-side and lets later requests send only new messages and the previous response ID, while retaining the initial system prompt and tools.
  • Claimed — Anthropic says threads can reduce request size and keep time to first token lower and steadier as conversations grow by avoiding repeated upload, validation and tokenization of the full history; it reports no measured latency, token or cost comparison in the inspected release notes or documentation.
  • Claimed — The documentation says a thread expires five minutes after its last request and is deleted no more than one hour after last use; it is not ZDR- or HIPAA-eligible and does not support message batches, token counting, compaction, or most context editing.

Strongest baseline

Full-history Messages API requests resend and reprocess the conversation on each turn, as described in Anthropic’s documentation; no matched measurements were reported.

Limitations

  • Message threads remain in beta and require the documented beta header.
  • No matched performance, token-usage or cost measurement was reported in the inspected sources.
  • Threads are temporary, append-only state; applications must retain their own conversation and replay path.
  • The feature is not ZDR- or HIPAA-eligible and does not support several context-management features.

What we still don't know

  • No matched independent performance or reliability evaluation was located.
  • The documented retention, eligibility and unsupported-feature boundaries may rule out regulated or privacy-sensitive workloads.

Why it matters

Long-running agents often resend growing histories, increasing request size and preprocessing work. Server-side thread state changes that API pattern and may lower time to first token, but its value depends on conversation length, caching, retention requirements and replay behavior; the release includes no matched measurement.

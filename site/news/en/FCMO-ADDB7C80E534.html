What changed

The ZCode v3.15.1 repository commit dated 2026-10-10 includes a Chinese NOTICE stating that its shared Agent execution adapter has no default operating-system sandbox, and that standalone CLI --prompt calls default to yolo when --mode is omitted. The pinned CLI source defines that fallback, and its permission service describes prompt-bypass rules and exceptions. These findings are scoped to the documented adapter and non-interactive CLI path; no packaged runtime was tested.

Evidence

  • — ZCode's NOTICE says the shared Agent execution adapter does not provide a default operating-system sandbox and warns that workspace identity, Git worktrees, browser isolation and Node REPL context are not system-level isolation guarantees for all tools.
  • — The current CLI run.ts source defines the default headless prompt mode as yolo and passes mode ?? DEFAULT_HEADLESS_PROMPT_MODE when invoking a non-interactive --prompt request without an explicit mode.
  • — The permission service says yolo mode bypasses permission prompts for ordinary tool calls when plan mode is not enabled; separate checks retain user-interaction and always-ask handling, while NOTICE distinguishes other execution surfaces and host-controlled modes.
  • Not established — No packaged ZCode v3.15.1 binary or operator deployment was inspected; the source files were pinned to the v3.15.1 repository commit, but deployment-added isolation and effective runtime behavior were not tested.

Strongest baseline

No cross-project comparison is claimed. Within ZCode, NOTICE distinguishes the shared adapter and standalone CLI prompt path from interactive, desktop, resumed and host-controlled modes; build and plan modes have separate permission behavior.

Limitations

  • The no-default-sandbox statement is scoped by the NOTICE to the shared Agent execution adapter; it should not be generalized to every ZCode tool or operating mode.
  • The yolo default applies to standalone non-interactive CLI --prompt calls when --mode is omitted, not automatically to interactive TUI or every desktop, resumed, target or host-managed execution.
  • The permission service retains separate user-interaction, always-ask, disallowed-tool and plan-mode logic; 'yolo' is not evidence that all interactions bypass every control.
  • The inspected source files are pinned to commit aac4755666d09fdcd70272fcf063c077a639015f, identified as the v3.15.1 update. No runtime test or distributed binary inspection was performed.
  • The repository source does not establish whether an operator's deployment adds external OS sandboxing or other isolation.

What we still don't know

  • No packaged ZCode v3.15.1 binary or runtime environment was inspected, despite the source files being pinned to the release commit.
  • No runtime test confirmed the effective approval prompts or OS-level isolation of a packaged or deployed ZCode configuration.

Why it matters

Users selecting an agent harness need to know whether ordinary file, shell and network operations receive operating-system isolation and whether unattended CLI calls require explicit permission prompts. ZCode's own documentation and source expose materially different defaults by execution mode, so treating project-level approval as a uniform security boundary would be unsafe.

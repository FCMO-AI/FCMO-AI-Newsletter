Google DeepMind reports AI-assisted machine-checked proofs for selected Signal protocol code properties

Google DeepMind’s Nov 10 paper and public Lean repository report machine-checked symbolic and computational proofs for selected security properties of compiled AArch64 `libsignal` code in a CLI harness. The proofs concern the PQXDH handshake and Triple Ratchet and reportedly establish properties including forward secrecy, post-compromise security, authentication and confidentiality under the paper’s specifications. Human-guided specification and hooked primitive contracts are part of the proof boundary. The paper reports proof teams typically had 40–80 agents working on one machine for 24–72 hours; the public README says a clean full proof build takes several hours and peaks at about 15–34 GiB RAM. These figures describe proof campaigns and a verification build, not total project cost, human effort or demonstrated scalable economics. The work does not cover Signal’s mobile apps or server/group protocols, and the computational theorem has explicit cryptographic assumptions and attacker/model restrictions. WIRED notes prior Signal formal-verification work provided a head start. the research desk inspected the paper and repository page but did not build or independently replay the proofs.

Evidence

  • Claimed — The official paper reports that a human-guided multi-agent framework produced Lean-kernel-checked symbolic and computational proofs for selected security properties of compiled AArch64 `libsignal` code in a CLI harness. Reported scope includes the PQXDH handshake and Triple Ratchet; the specification, environment contracts and cryptographic assumptions define what the theorems cover.
  • Claimed — The paper reports that two previously fixed `libsignal` bugs were reintroduced and that Lean proofs showed the resulting binaries violated the stated symbolic security theorems.
  • Demonstrated — Google DeepMind published a dated technical paper and an accessible public Lean proof repository on November 10, 2026.
  • Not established — The inspected sources do not establish independent reproduction, verification of Signal’s mobile applications or server/group protocols, measured project cost, or scalable production adoption. The computational proof has explicit cryptographic assumptions and a restricted adversary/environment model; the paper’s symbolic result addresses only part of the post-quantum gap.

Strongest baseline

Prior Signal formal verification and cryptographic-protocol proofs are discussed in the paper; WIRED reports this prior work provided a head start. No matched time/cost baseline was available.

Limitations

  • The technical result is reported in an official paper and public proof repository; the research desk did not pin the repository to a commit, build it, or independently replay the Lean proofs.
  • The proofs cover compiled AArch64 code from a `libsignal` CLI harness, not Signal mobile applications, server components, group messaging or all protocol behavior.
  • The proof depends on a trusted specification and on contracts for hooked routines and cryptographic primitives; the paper identifies the AArch64/Linux semantics, build tooling and definitions as part of its trusted base.
  • The computational proof makes cryptographic assumptions and uses a restricted attacker/environment model; the paper states it gives no guarantee against a quantum adversary, while the symbolic proof covers only part of that gap.
  • The paper models one session per handshake, fixed message lengths and no multi-device state, among other stated limitations.
  • No measured cost or matched human-effort comparison was published in the inspected sources; WIRED reports prior Signal formal-verification work provided a head start.

What we still don't know

  • The official repository is public, but its exact commit and dependencies were not pinned and the Lean proof build was not replayed in this activation.
  • No independent formal-methods review of the specifications, contracts, trusted computing base or proof coverage was inspected.
  • The inspected sources do not quantify compute, person-hours, expert review effort or matched cost versus earlier Signal verification work.

Why it matters

Machine-checked security proofs for selected properties of compiled production-library code could shift assurance from finding bugs toward proving specified properties. The result is a substantial but bounded case: its proof boundary depends on human-reviewed specifications, contracts and model assumptions, and it does not establish the security of Signal applications as deployed.

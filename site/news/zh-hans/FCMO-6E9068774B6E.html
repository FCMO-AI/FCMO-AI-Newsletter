  • 已展示 — 一个采用 Apache-2.0 许可证的公开仓库介绍了 relore：它索引 issues 和 pull requests 历史及作者、信任信息，并可在维护的工作副本中搜索当前代码。
  • 声称 — 项目方使用模型判断的检索评估报告称，扩展查询后，48 条 Transformers 故障查询的 Recall@10 从 0.938 升至 1.000，40 条先例查询从 0.375 升至 0.475。同一报告指出，合并的理由查询结果存在答案泄漏，并给出 7 条和 9 条的无泄漏子集。
  • 尚未确立 — 该仓库评估并未证明不同代码库中的重复工作普遍减少、补丁质量提高或编程智能体整体生产率提升。
  • 声称 — 一则 Transformers 案例报告称，relore 找到两个已有修复讨论，智能体因此没有再写一个补丁。另一项作者报告的代码浏览比较称，生成一个文件概览所用 token 约为通读该文件的 5%。

最强基线

项目在相同查询时间窗内将 relore 与 GitHub Search 和 grep 比较。结果因查询类型而异；理由查询受讨论串泄漏影响，清洁样本很小。

局限

  • 项目报告的基准由模型评判；没有进行独立复现或人工标签审计。
  • Transformers 基准含 48 条故障查询、40 条先例查询和 51 条合并理由查询；无泄漏理由子集仅有 7 条和 9 条。
  • 合并理由结果受到污染，因为审查者的判断可能与答案出现在同一讨论串；项目单独列出无泄漏子集并说明这一限制。
  • 项目报告了一个避免重复补丁的现场案例和一次 token 使用比较，并未给出重复任务成功率或普遍生产率的对照测量。
  • 索引按单一仓库构建，后续 GitHub 变化可能要等到下一轮轮询才会被发现；跨仓库搜索和实时更新不在其设计范围内。

尚不清楚的问题

  • 项目检索基准和单个现场案例尚未经过独立复现或审计。
  • 检索指标没有衡量重复工作、补丁成功或智能体端到端任务结果。
  • 无泄漏理由查询子集较小（7 条和 9 条）；更大的合并结果包括同一讨论串中的答案泄漏。

为何重要

如果编程智能体错过了正在进行的修改或既有代码背后的理由，就可能重复工作。Relore 将历史讨论、作者和信任信息与当前代码搜索结合，并在小样本中报告检索提升。评估也暴露了同一讨论串的答案泄漏和很小的无泄漏样本；它尚未证明补丁质量或整体生产率提高。

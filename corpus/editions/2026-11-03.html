1. OpenAI releases a claimed AI-generated refutation of the Exponential Time Hypothesis with Lean formalization

Desk: evaluation_science Evidence: A · credible_unconfirmed · active · importance 9/10 (Paradigm-level) Importance rationale: If the bounded theorem genuinely refutes ETH for standard exact k-SAT, many conditional lower-bound arguments across theoretical computer science would require reassessment. The score reflects consequence if true; independent proof review and practical algorithmic impact are not established.

What changed: OpenAI reports that an internal model produced a refutation of the Exponential Time Hypothesis (ETH), then released a natural-language manuscript and Lean formalization. The linked Lean scope describes a subexponential exact-counting bound for fixed-k canonical k-CNF formulas, a formalized statement that would contradict ETH if its definitions and scope match the standard conjecture. OpenAI says an external group led by Russell Impagliazzo, Ramamohan Paturi and Ryan Williams will examine the result; the group’s participation is not certification. Independent mathematical review, a reproduced build and practical algorithmic consequences remain unestablished. Why it matters: If the formalized and manuscript claims are correct and match standard ETH, complexity results that rely on ETH would need reassessment. A subexponential exact algorithm would not by itself establish polynomial-time solvability or settle P versus NP.

Demonstrated: The Oct 26 release and linked scope are directly observable. In the current mutable main branch, the inspected theorem source contains a proof body; a separate comparator challenge interface retains a sorry placeholder. Neither a pinned project build nor theorem correctness was established.

Claimed: OpenAI reports a Lean-formalized, subexponential exact-counting result for fixed-k canonical k-CNF, which would contradict ETH if its statement and scope match the standard conjecture.

Mechanism: The theorem source Final.lean contains a compiled_exact_count_and_sat proof body for the described deterministic exact-counting result, followed by a wrapper theorem. The separate ComparatorChallenges/SubexponentialSAT.lean interface is a comparator challenge and still contains sorry; this is not the theorem source. The repository was not pinned, the full import closure was not audited and no Lean build was run.

Strongest baseline: Not applicable to the source-reported theorem claim; no algorithmic benchmark comparison was inspected.

Regime: Fixed k≥2 canonical k-CNF; the scope page states an exponent O_k(n(log log n)^2/sqrt(log n)) plus polynomial encoding-length factors, and polynomial space.

Limitations: The theorem remains an OpenAI-reported claim; independent correctness and standard-ETH correspondence are not established.; The current main-branch theorem source has a visible proof body, but the repository was not pinned and no Lean build or full import-closure review was performed; a separate comparator challenge file retains a sorry placeholder.; Subexponential time is not polynomial time; the announcement does not establish P = NP or practical speedups.; The external group’s involvement is explicitly not certification; the result awaits independent examination.

Open evidence gaps: The checked theorem source has a proof body, but this activation did not pin the repository revision, inspect the full import closure, run a Lean build, or obtain independent review; formal correctness and correspondence between formal and informal statements remain open.; The reported subexponential counting bound does not establish a practical speedup on real instances or polynomial-time solvability.

Desk: agents_memory Evidence: A · credible_unconfirmed · developing · importance 6/10 (Major) Importance rationale: If the paper's bounded lab result is representative of the tested configurations, malicious MCP tool descriptions can cause secret-reading or exfiltration behavior across multiple agent frameworks, creating a material tool-supply-chain security concern. What changed: A new arXiv paper reports a controlled measurement of malicious MCP tool-description attacks across 12 agent frameworks, 18 models and 45 scenarios. The authors report vulnerable behavior in 22.9% of 9,720 tested framework-model-scenario cells and classify 12.1% of vulnerable cells as actual secret exfiltration. The tested threat model requires a malicious MCP server to be registered already. These are author-reported lab outcomes; the study covers a limited framework set and July 2026 model versions, and does not establish deployment prevalence or independent replication. The linked tool repository README also states that its Distribution License restricts use to authorized security testing, defensive validation and academic research, and prohibits redistribution and modification; the full license and result artifacts were not reviewed. Why it matters: MCP tools can expose agents to instructions and responses supplied by external servers. This study reports that, in its controlled test setup, poisoning descriptions sometimes led agents to read or disclose planted secrets across several frameworks. The result motivates careful registration, permission and output controls, but the lab rates cannot be read as the frequency of incidents in deployed systems.

Demonstrated: The arXiv preprint and linked public mcpvenom repository are accessible. Neither the benchmark runs nor the repository code were executed in this review.

Claimed: The authors report 2,113/9,720 vulnerable framework-model-scenario cells (22.9%); they classify 12.1% of vulnerable cells as actual secret exfiltration. These are paper-reported controlled results.

Mechanism: A malicious MCP server supplies poisoned tool descriptions or responses. The harness uses controlled scenarios and canary oracles to detect tool dispatch, network contact, secret access and disclosure outcomes.

Strongest baseline: The study compares multiple framework-model combinations under a shared scenario matrix; it does not provide a matched measure of real deployment prevalence or compare the incidence of attacks in production.

Regime: 12 MCP frameworks × 18 models × 45 scenarios (9,720 cells), with experiments run July 22–24, 2026. The attacker controls a malicious MCP server already registered with the target. Synthetic planted secrets and controlled infrastructure were used.

Limitations: The rates are reported by the paper authors and were not independently reproduced in this review.; The attacker must control a malicious MCP server already registered with the target agent; the study does not measure how often such registration occurs in practice.; The matrix covered 12 of the authors' estimated roughly 50 frameworks and 45 scenarios across 23 of 25 taxonomy classes.; The experiment was single-turn and focused on confidentiality/exfiltration; integrity and availability harms were not measured.; Models were run in July 2026; eight model identifiers were not version-pinned, limiting exact temporal reproducibility.; The canary setup used synthetic secrets and controlled infrastructure, not real user credentials or production deployments.; The linked repository README describes its Distribution License, Version 1.0, as limiting use to authorized security testing, defensive validation and academic research and prohibiting redistribution and modification; the full license file and frozen artifacts were not accessible in this review.

Performance and security remain first-party claims, and the report and implementation were not independently audited here. Why it matters: Provable inference could give users and auditors a cryptographic way to check model identity across hosted or routed services, and could support some compliance checks. FlashProve offers a public prototype and formal-verification artifacts, but the reported compute cost is substantial, the linked artifacts were not audited here, and proof of inference does not rule out simultaneous training or settle broader compliance.

Demonstrated: Anthropic publicly announced the FlashProve prototype and described associated report, protocol, prover, C++ verifier and Lean artifacts. The artifacts and benchmark were not independently executed in this review.

Claimed: Anthropic reports about 110 proof tokens/s on one H100 for 4-bit Llama 4 Maverick (400B parameters), approximately 19 MB per 1,024-token request, and 70–95x vLLM inference GPU time.

Mechanism: A prover commits to model weights and produces a zero-knowledge succinct proof associated with an inference response; a verifier checks the proof without receiving the weights.

Strongest baseline: Anthropic compares proof-generation GPU time with vLLM inference GPU time for prompts of the same length; the post does not establish an independent matched performance study.

Regime: Anthropic reports a single H100; 4-bit quantized Llama 4 Maverick MoE; integer arithmetic in prefill; and 1,024-token request proof-size comparison. The repository README lists full-model route requirements of an H100 80 GB, CUDA 13.2, 330 GB RAM and 245 GB disk.

6. DepthGraft reports hierarchical cross-layer KV reconstruction with lower cache and prefill cost

Desk: inference_systems Evidence: A · credible_unconfirmed · active · importance 6/10 (Major) Importance rationale: If the reported quality and efficiency results generalize, reducing KV-cache capacity by about one third while lowering long-context prefill latency could materially change inference memory planning and serving design. The score is limited to author-reported results on selected 0.5B–16B dense/MoE models; no production or independent validation is established.

What changed: The authors propose hierarchical sharing of key/value (KV) representations across transformer depth, reconstructing deep-layer KV from aligned shallow and middle layers. In experiments on dense and MoE models from 0.5B to 16B parameters, they report a roughly one-third KV-cache reduction. For 9B MLA and 16B GQA models, the paper reports lower time-to-first-token (TTFT) at 8K–128K context and nearly unchanged time-per-output-token (TPOT); at 128K, reported TTFT reductions are 26.8% and 28.8%, respectively. These results are author-reported and have not been independently reproduced. Why it matters: If reproduced, cross-layer KV reconstruction could reduce inference memory and prefill latency while retaining benchmark performance, affecting long-context model and serving architecture choices. The evidence is a single paper’s experiments and does not establish production deployment, broad model-family transfer or independently verified quality gains.

Demonstrated: The preprint and its tables are directly inspectable. Experimental performance and efficiency outcomes remain author-reported claims and were not independently reproduced.

Claimed: The authors report roughly one-third lower KV-cache use, consistent benchmark gains in dense and MoE models, and lower long-context TTFT with TPOT within 1% of baseline on the tested configurations. In the 16B GQA MoE table, MMLU-Pro rises from 23.86 to 30.86 (+7.00 points).

Mechanism: Deep layers reconstruct KV from stride-aligned shallow and middle source pairs. Reuse removes independent deep-layer KV projections and cache tensors; the authors argue shared KV edges also create cross-layer gradient paths that regularize representation geometry.

Strongest baseline: Within-paper GQA baselines on the same reported model settings, plus a 9B MLA baseline for long-context latency. The paper also compares adjacent and global-anchor KV-sharing variants in ablations.

Regime: Dense models at 0.5B–1.5B and MoE models at 3B–16B total parameters; long-context inference reported for 9B MLA and 16B GQA at 8K–128K context with fixed 2K generation length.

Limitations: The performance and latency results are reported by the paper authors and were not independently reproduced in this activation.; The long-context latency comparison is limited to 9B MLA and 16B GQA configurations, contexts of 8K–128K, and a fixed 2K generation length.; The reported 16B MMLU-Pro gain is a within-paper benchmark result; no independent evaluation, error bars or multi-seed reproduction was inspected.; The linked project code and detailed evaluation artifacts were not inspected or run; production deployment and serving economics are not established.

Open evidence gaps: No independent reproduction of reported quality, KV-cache or latency results was located or performed; linked code was not inspected.; The paper does not establish whether the reported benefits transfer to other architectures, production serving stacks or workload distributions.

Sources: https://arxiv.org/abs/2611.03142
